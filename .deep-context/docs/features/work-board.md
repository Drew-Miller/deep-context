# Work tracking

A phase or standalone request has a descriptively named Markdown execution file in its current lane. Use headings for scope, ordered requests, implementation and evidence. Split it into a subject folder only when multiple documents are useful; follow the [folder standard](../requirements/readable-folders.md). Its short stable ID survives reorders and moves. Record its feature, origin and any prerequisite ticket IDs separately. A user idea can stand alone; a ticket or document can also be its origin. Link durable outcomes to the work that produced them.

- Order backlog and active tickets by priority. Reordering changes visible numerical prefixes and repairs references. The order is independent of dependencies.
- Before adding a ticket, compare compact summaries in active and backlog, then completed work. Open only strong candidates. Aim for under a minute, present at most three concrete overlaps and ask whether to expand an existing ticket, create a follow-up or keep a separate ticket. If the search was bounded or incomplete, say what it covered.
- Starting blocked work names the unfinished prerequisites and asks the user to choose. Dependencies can cross feature boundaries. Completing a prerequisite can make a ticket ready; the agent tells the user and leaves the choice to start it with them.
- Before marking work complete, verify the deliverable and record lasting requirements or decisions in docs. Record the finish time and move the ticket to the front of completed work. Explicit removal is available; review surviving links and dependencies before clearing a ticket.

## Record types

Follow the canonical [plans, phases and work-item definitions](../requirements/plans-phases-and-work.md). Phase files are the default execution homes; concrete requests are ordered sections inside them. Standalone requests may also appear on the board. A lane shows the status of its record, while the overview plan links related phases and orders their execution.
